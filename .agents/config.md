Recommendation
[Speculative recommendation] Keep one backend YAML store after Phases 1–6, but stop using one ownership/default policy for every field. Do not adopt bbolt or another embedded DB.
The immediate architectural defect is not the flat file; it is that the backend, frontend defaults, and frontend cache can each act as an authority. The lowest-risk path is:
1. Keep ~/.linuxio-config.yaml, its sidecar flock, and WriteFileAtomic as the durable transaction boundary.
2. Split the model logically into UI profile values, consequential client settings, and backend/host settings, with different default and recovery policies.
3. Make config.get the authoritative effective configuration. Remove the frontend’s independent full AppConfig default copy; retain only a minimal, non-authoritative paint/bootstrap fallback.
4. Make the browser cache a bootstrap cache only and always reconcile with config.get once connected. Never let cached Docker/jobs values suppress a backend read.
5. If protection against whole-document corruption is required beyond Phases 1–6, evaluate a validated last-known-good YAML copy before introducing a second store or DB.
6. Move cosmetics client-only only after explicitly deciding that cross-browser/device continuity is not a product requirement.
This recommendation assumes current server-backed preference continuity is intentional: ConfigProvider itself describes the backend as the durable store ([ConfigProvider.tsx (line 343)](/home/miguelmariz/LinuxIO/frontend/src/contexts/ConfigProvider.tsx:343)). If LinuxIO instead wants appearance to be deliberately device-local, the preferred end state changes to client-only cosmetics, not a second backend preference file.

Alternative 1: one file, one mechanism
Verdict: recommended, but only with an authority/cache layer above Phases 1–6.
- [Source-verified] Phases 1–6 deliberately do not resolve frontend/backend default ownership ([bridge-config-simplification.md (line 349)](/home/miguelmariz/LinuxIO/docs/TODO/bridge-config-simplification.md:349)). Therefore the plan is sufficient for the YAML package’s correctness but not for the complete configuration architecture.
- [Speculative] A logical UIPreferences/ConsequentialSettings/BackendSettings split can give each group a separate validator, default policy, and ownership documentation without changing the physical transaction boundary.
- [Speculative] The remaining physical conflation cost is failure coupling: an entirely unparseable document is still intended to be replaced with full defaults ([bridge-config-simplification.md (line 218)](/home/miguelmariz/LinuxIO/docs/TODO/bridge-config-simplification.md:218)). Cosmetic syntax damage therefore shares a recovery fate with docker.folders. One lock and full-file rewriting are not evidenced performance problems; the store is small and per-user.
- [Speculative] The single file retains valuable properties: one migration stream, one lock, and one all-or-nothing config.set. A single request can currently mutate app, Docker, jobs, and dismissals before one store commit ([apply.go (line 10)](/home/miguelmariz/LinuxIO/backend/bridge/handlers/config/apply.go:10), [config_operations.go (line 22)](/home/miguelmariz/LinuxIO/backend/bridge/handlers/config/config_operations.go:22)).
The frontend changes are essential even if storage remains untouched:
- Cache only the cosmetic bootstrap subset, preferably sparse overrides.
- Always call config.get once the mux is available and reconcile cached appearance afterward.
- Do not fabricate Docker/jobs values when the backend has not loaded.
- Do not persist a fully resolved default object: that makes an old default indistinguishable from an explicit user choice.
- Treat minimal offline paint values as failsafes, not canonical defaults.
Alternative 2: two flat files
Verdict: real fault isolation, but not justified yet unless server-side UI portability and independent recovery are both explicit requirements.
A second physical file changes substantially more than two nested structs:
- [Speculative] Separate files provide independent parsing, corruption recovery, migrations, locks, and write frequency. A bad preference file can be reset without touching Docker folders.
- [Speculative] Two substructs in one YAML provide none of that physical isolation. They still share the parser, file lock, atomic rename, and document-wide syntax failure.
- [Speculative] Separate files introduce two initialization paths, two flocks, fixed lock ordering, and a cross-file transaction problem. WriteFileAtomic is atomic for one destination only ([atomic.go (line 45)](/home/miguelmariz/LinuxIO/backend/common/utils/atomic.go:45)). A crash between two renames can partially commit a mixed request.
- [Source-verified] Mixed-domain requests are allowed by ConfigSetPayload, and ConfigSetResult can report only one path ([contracts.go (line 461)](/home/miguelmariz/LinuxIO/backend/bridge/apischema/contracts.go:461), [models.go (line 1043)](/home/miguelmariz/LinuxIO/backend/bridge/apischema/models.go:1043)). A split must therefore explicitly choose one of:
  - reject cross-domain patches;
  - introduce separate endpoints;
  - document partial-commit semantics; or
  - add a journal/manifest, which largely defeats the hoped-for simplicity.
A safe migration would need to acquire locks in a fixed order, validate the legacy document first, write and strict-reread the critical file with the exact Docker folder list, then write preferences and publish a completion marker. An absent new file must never be interpreted as “fresh defaults” during a partial migration. The old YAML should be retained for rollback. This follows the existing shim precedent ([bridge-config-simplification.md (line 191)](/home/miguelmariz/LinuxIO/docs/TODO/bridge-config-simplification.md:191)) and its absolute prohibition on silently resetting Docker folders ([bridge-config-simplification.md (line 391)](/home/miguelmariz/LinuxIO/docs/TODO/bridge-config-simplification.md:391)).
The existing wire can remain unchanged if Settings stays as the in-memory aggregate assembled from both stores. The explicit adapter already separates persistence types from apischema.AppConfig ([contracts.go (line 8)](/home/miguelmariz/LinuxIO/backend/bridge/handlers/config/contracts.go:8)), and the parity guard can continue checking that aggregate ([contracts_test.go (line 11)](/home/miguelmariz/LinuxIO/backend/bridge/handlers/config/contracts_test.go:11)).
Alternative 3: client-only cosmetics
Verdict: technically clean and the preferred split if LinuxIO deliberately chooses device-local appearance. It is not behavior-preserving.
- [Reproduced] No backend operational reader depends on the pure presentation fields, so backend execution would not break.
- [Speculative] What is lost is fresh-browser/profile/device continuity, server-side backup/restore, and filesystem inspection by an administrator. Current “admin visibility” is not an application feature: the config routes are scoped to the active session, while the YAML is machine-owned and not documented as user-editable ([handlers.go (line 27)](/home/miguelmariz/LinuxIO/backend/bridge/handlers/config/handlers.go:27), [bridge-config-simplification.md (line 11)](/home/miguelmariz/LinuxIO/docs/TODO/bridge-config-simplification.md:11)).
- [Source-verified — external] Browser storage is origin/profile-local. localStorage persists across browser sessions, whereas sessionStorage ends with the page session; IndexedDB is also same-origin and needs its own schema/versioning (HTML storage standard, IndexedDB documentation).
- [Speculative] localStorage is sufficient for this small preference envelope; IndexedDB provides no useful query or volume advantage. LinuxIO already has a validated, best-effort localStorage helper specifically for per-browser view state ([persistedState.ts (line 1)](/home/miguelmariz/LinuxIO/frontend/src/utils/persistedState.ts:1)).
Simply promoting configCache.ts would be unsafe. A real client-owned preference store should be:
- namespaced per LinuxIO username;
- versioned and runtime-validated per field;
- sparse, storing only deviations from current UI defaults;
- independently repairable by field;
- explicit about whether logout retains or clears preferences;
- reconciled across tabs if that matters.
Truly removing cosmetics from the backend eventually requires a deliberate API change because theme, primaryColor, and sidebarCollapsed are currently required response members ([models.go (line 1468)](/home/miguelmariz/LinuxIO/backend/bridge/apischema/models.go:1468)). The safe sequence would be one compatibility release that imports existing backend values into an empty local envelope, followed by a separately reviewed apischema/generated-TypeScript change. It must not happen incidentally during storage refactoring; Go owns the wire contract and generation flow ([api-contract.md (line 28)](/home/miguelmariz/LinuxIO/docs/api-contract.md:28), [api-contract.md (line 506)](/home/miguelmariz/LinuxIO/docs/api-contract.md:506)).
Alternative 4: bbolt or another embedded DB
Verdict: reject for this problem. Upstream bbolt is not merely overkill; its locking model is a poor fit.
There is also an important correction to the premise:
- [Source-verified — external] The referenced FileBrowserQuantum page now describes v2 as moving from BoltDB/Storm to SQLite plus a state layer. Its reasons are activity history, reporting, fine-grained permission lookups, cross-user/time/event queries, caching on busy instances, and centralized writes—not simple preference persistence (FileBrowserQuantum architecture).
- [Speculative] FileBrowserQuantum’s documented single server database, multi-user management, cross-user queries, and process-lifetime caches describe a shared multi-user service. That is materially different from LinuxIO’s one small per-user aggregate and one bridge per login.
- [Source-verified — external] bbolt takes a file lock for the lifetime of a read-write Open; another process opening the same database waits until the first closes unless a timeout is configured (official bbolt README). Multiple read-only processes block a read-write opener.
- [Speculative] A conventional long-lived bbolt handle would let the first LinuxIO bridge hold the user database for its entire session and make a second same-user bridge hang or fail. Opening and closing around every operation would recreate today’s sidecar-lock serialization with binary storage and more machinery. Centralizing ownership in a daemon would be an architectural service change.
- [Source-verified] No DB engine is present in the backend’s dependency lists ([go.mod (line 5)](/home/miguelmariz/LinuxIO/backend/go.mod:5)).
Operationally, bbolt does offer consistent hot backups and a check/inspection/surgery CLI (backup documentation, official CLI). But LinuxIO would have to build or document DB-aware backup, restore, ownership, validation, and recovery procedures. Direct text-editor inspection and repair would disappear; the current YAML retains that affordance, including comments on clean starts ([bridge-config-simplification.md (line 183)](/home/miguelmariz/LinuxIO/docs/TODO/bridge-config-simplification.md:183)).

No C1–C9 defect requires a database. The only broadly relevant DB benefits—crash-safe commit and serialization—already have narrower owners in WriteFileAtomic and the flock once Phases 1–6 land.
Revisit a DB only when LinuxIO gains independently queried records, audit/history/reporting, cross-user administration, or multi-record transactional invariants. At that point SQLite is the more relevant candidate; it is also what FileBrowserQuantum selected for those needs.
Additional alternative: last-known-good critical config
[Speculative] A validated last-known-good copy is a more proportionate response to the remaining whole-document blast radius than a second live store or DB. It could preserve the previous known-good Docker folders when the current YAML becomes globally unparseable, while retaining text inspectability and the existing single-lock/API transaction.
This would deliberately alter the Phase 1 “replace an unparseable file with defaults” policy, so it should be a separately reviewed follow-on—not smuggled into Phases 1–6. Recovery should quarantine the bad file, report the event, strict-read the backup, and never silently manufacture Docker folders.
Proposed sequence
1. Finish Phases 1–6 unchanged. Do not carry the dead probing/repair apparatus into the ownership work; the plan already removes or narrows it ([bridge-config-simplification.md (line 234)](/home/miguelmariz/LinuxIO/docs/TODO/bridge-config-simplification.md:234), [bridge-config-simplification.md (line 252)](/home/miguelmariz/LinuxIO/docs/TODO/bridge-config-simplification.md:252)).
2. Write the ownership contract before changing storage.
   - config.get is authoritative for effective, server-portable configuration.
   - Backend/host defaults, especially dynamic Docker paths, are backend-owned.
   - UI implementation defaults for deliberately absent optional values live at the UI use site.
   - Cross-boundary UI default selections are defined once by the API/default contract, not independently in settings.go and ConfigProvider.
3. Separate frontend bootstrap from authoritative config. Cache only what prevents a paint/theme flash, always fetch after connection, and disable backend-dependent behavior until that fetch succeeds.
4. Introduce logical policy boundaries inside the aggregate. Cheap UI invalidity may fall back per field; consequential settings must be conservatively validated and never silently reset during migrations. Keep the one lock and one atomic file.
5. Decide UI portability explicitly.
   - If preferences should follow the Unix user: retain backend persistence; reconsider a second preference file only if independent fault recovery becomes a demonstrated need.
   - If preferences should follow the browser/device: migrate pure cosmetics to a versioned sparse localStorage envelope, then make the required API change separately.
6. Consider last-known-good protection for the critical YAML. This directly addresses the remaining Docker-folder blast radius.
