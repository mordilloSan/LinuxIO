# Privilege Pattern

Privilege is route metadata. Handlers should not perform the normal route privilege gate themselves.

## Rule

Declare privileged operations in the relevant `backend/bridge/handlers/<domain>/handlers.go` binding entry:

```go
var api = apischema.Bindings(
    apischema.Call[apischema.NoRequest, apischema.NoResponse](
        "monitoring.restart",
        apischema.Privileged(),
    ).HandleVoid(handleRestart),
)
```

`apischema` applies that metadata when the route is registered. The dispatcher checks `req.Session.Privileged` before the handler or runner starts. Forbidden starts are typed dispatcher errors and are logged centrally.

## What Belongs In Handlers

Handlers may still validate operation-specific policy:

- whether a requested resource exists
- whether a request field is allowed
- whether a system capability is available
- whether a user-visible operation should be rejected for domain reasons

Handlers should not duplicate the route-level admin check.

## Choosing Privileged Routes

The rule: a route whose handler needs root must be declared `Privileged()`. The bridge runs as the logged-in user and stays root only when sudoers permits it, so a route that writes under `/etc` or `/var/lib`, mounts or unmounts, issues block-device or filesystem ioctls, or talks to systemd, NetworkManager, Docker, libvirt, PackageKit or the account database only works in a privileged bridge. Without the guard a non-sudo session sees the route, starts it, and gets a permission error from the host part-way through instead of a 403 before anything ran. It is not a privilege escalation, but it is a bug: declare the guard with the route, not inside the handler.

Docker is a fixed case. Access to the Docker socket is root-equivalent, so the deployment keeps the `docker` group empty and only a sudo-authorized bridge or the root job host may reach it. Every Docker write declares `Privileged()`: mutations, task routes, and anything else that changes containers, images, networks, volumes, compose stacks or daemon settings. Do not make a Docker write unprivileged on the grounds that members of the `docker` group could run it. Docker reads are not covered by this rule.

Read-only system inventory can usually remain unprivileged unless it exposes sensitive information.

Routes that change the host through polkit-gated D-Bus calls (systemd, NetworkManager, hostname, timedated, login1) are privileged like the rest. polkit might let a user without sudo run some of them, but the answer would differ from host to host; LinuxIO gives one answer, a 403 before anything runs.

### What is enforced

The dispatcher enforces a declared guard, and `TestChangingRoutesArePrivilegedOrListed` in `backend/bridge/apischema/schema_test.go` enforces that the guard is declared. It walks every route: each `Mutation`, each duplex stream and each `Call` that is not `RetrySafe()` must be `Privileged()` or be named in `unprivilegedChanges`, the list in that file, with the reason it needs no root. A stream counts because it can change the host as much as a mutation can: `container.open` starts a process inside a container. The test also fails on a listed route that became privileged or no longer exists, so the list stays true.

A new route that changes the host therefore fails the test until it declares the guard or is added to the list. What is on the list today:

- the file browser's routes, which act on the session user's own files as that user;
- the Assistant routes, which run the session user's own `claude` CLI and write only under that user's home ([Assistant](./AI-assistant.md#plugins));
- `terminal.open`, the session user's own shell;
- `tasks.cancel`, `tasks.watch`, `tasks.data` and `tasks.events`, the caller's own jobs;
- `config.set`, `config.set_ui` and the two `system.dismiss_*` routes, which write the session user's own settings (`config.set` refuses its three root-only Docker fields in the handler: `docker.requireMountsForFolders`, `docker.waitForHostIPs` and `docker.hostIPs`, which end in a systemd drop-in for `docker.service`, and `docker.folders` too while the mount setting is on; see [Bridge Configuration Storage](./config-storage.md#docker-startup-settings));
- reads that are not `RetrySafe()`: the Docker update checks and icons, the log and download streams, `network.get_network_info` and `system.get_health_summary`.

### Root acting in the session user's folders

For an admin the file browser's changes run as root, in the root job host or, for uploads, in the root bridge, on folders a process of the session user can rearrange while the change runs. A process that swaps one of that user's folders for a symlink would otherwise point root at any folder on the system. So creating a file or a folder, delete, trash and restore, copy, move and rename, chmod and chown, compress and extract, and every upload and editor save, with or without `owner`, reach the folder they act in one name at a time from `/` and follow a symlink only where nobody but root can have planted it: in a folder root owns that no group or everyone may write, such as `/home -> /var/home` or `/bin -> usr/bin`. A link in any other folder is refused with 403. That covers the session user's own folders, and equally another local user's or a service account's (`/home/v`, a `/var/www` that belongs to `www-data`): the owner of a folder can put a link in it, and an admin who compresses, uploads or restores there would otherwise be sent wherever that account chose. It includes a link made on purpose: an admin whose `~/Documents` is a link to another disk cannot change files through that path as root, and uses the real path instead. The refusal names it, `/home/a/Documents is a link to /mnt/data/Documents. Open that folder to make this change`, which tells the admin nothing `readlink` would not; the page shows it in the operation's error toast, or per item in a batch's failure list (which shows the first five), with an "Open the real folder" action that opens what the link points to, found in the whole list of failures and not only in the five shown (raised by a job of the Trash it leaves the Trash for that folder, as opening any folder from there does, and raised by a permission change it closes an open Permissions dialog first, so the folder does not change behind it; `frontend/src/utils/linkRefusal.ts` finds the path by the refusal's wording, and a test there fails when the wording changes). There is no "follow it anyway": the link can change between the question and the change, so the way through is to work in the real folder, where the admin sees what they act on. A save without `owner` writes through a link at the file itself, as an editor does, under the same rule. Below that folder everything is reached through open handles without following a symlink (`openat` with `O_NOFOLLOW`, `renameat2`, `linkat`, `fchownat`, and a chmod or a removal through the handle of the entry or its folder), so a folder swapped for a link mid-operation fails the operation or is never entered. chmod follows a link at the item itself, as `chmod(1)` does, under the same rule. A new file is made with `O_EXCL`, so a create never truncates what is already at its name. An upload writes into a buffer made that way beside its target and its task holds that buffer open from its creation to the commit, across every chunk and every reconnect of the data stream; the commit, or the cleanup of a failed, cancelled or abandoned upload, closes it, and a batch holds only the buffer of the file it is receiving. Every chunk, the owner and the mode go through that handle, so a process able to write the folder that deletes the buffer and keeps a file of its own at the name receives none of the upload, on every filesystem: a reopen by name would have to tell the two files apart, and ext4 gives a deleted file's inode number to the next file created. The commit links or renames by name, since rename has no form that takes an open file, so before the owner and mode are set and again just before the commit the name must still be the held file, compared on device and inode, whose number the filesystem gives no other file while the buffer is open (`checkUploadBuffer`); otherwise the upload, or that file of a batch, fails, and a buffer refused at the first check is still root's and private. A swap between that check and the rename can still put the swapping process's own file at the target, which a process able to write the folder can do anyway; root never writes to that file or hands it over. An upload that replaces a file reads the owner and mode it keeps, and removes the buffer of a cancelled upload, through the handle of the folder it commits in, so a folder swapped for a link lends it no other file's owner or setuid bit. A bridge that is not root acts as the user and follows the user's links as any program of theirs would, and a root session has no rule applied, since its user is no less trusted than the bridge (`linksafe.OpenDirNoUserLinks`, `linksafe.OpenNearestDirNoUserLinks`, `linksafe.Plantable`, `linksafe.ActingFor`, in `backend/bridge/internal/linksafe`).

The rule has two limits of its own:

- It trusts the owner and mode the filesystem reports, so a FUSE mount with `allow_other`, or a network mount, that presents a user's folder as root's passes it.
- It tests only the folder that holds the link, so a folder of root's holding root's links that sits inside a folder a user can write can be renamed by that user, who then decides which name leads to it.

An extract opens its archive once, under the same rule and before it makes anything (`services.OpenArchive`), and checks, measures and reads it through that handle: a link the session user could have planted at the archive's name, or on the way to it, is refused, so a link in their folder to an archive only root can read never hands them its content. Only a regular file is opened as an archive; a folder, a FIFO or a device is refused with 400.

Root removes a folder by name only when the name still holds the folder it means. A replace sets the old entry aside under a `.linuxio-replaced-` name and removes it once the transfer is done, a failed copy removes what it made, and an aborted extract removes its destination; each of those names sits in a folder the session user may write, where a process of theirs can rename another folder of that folder onto the name, also one whose content they could not delete. So the removal opens what is at the name without following a link and empties a folder only when it is root's to empty (`removeAllAtIf` in `services/trash.go`); otherwise it leaves the folder and logs a warning. Under a set-aside name no folder is: a folder is merged into, never replaced, so the entry set aside is not one. At a destination it is a folder whose device and inode are those of a folder the copy made (`copyState.made`) or of the destination the extract made, and `mkdirat` returns no handle, so a folder counts as made only when it was empty when root opened it. An entry that is not a folder is unlinked by name, which whoever can rename an entry in that folder can do as well; a copy that failed because a file already held its name leaves that file, which is another writer's. When the entry a failed replace set aside cannot be put back, because its name is taken, the operation's error says under which name it is kept.

A compress reads its sources the same way (`services.ArchiveSources`): a source named through a link the user could have planted is refused, and below a source folder everything is read through handles. A link in a folder that is not root's alone is left out of the archive, which root creates readable, and listed in the result's `failed`, so the page reports it as the compress finishing with failures; any other link is read as the archive code always read links, a link to a file adds the file and a link to a folder is left out. A FIFO, socket or device is left out. The size estimate behind the progress bar reaches and walks the sources the same way, so a planted link to `/` is not measured; a link is not counted. A download of several items as one archive (`filebrowser.archive`) goes to the admin's browser, not into the user's folders, and still reads as the user's own programs would. A download reads regular files only: a FIFO, socket or device, or a link to one, is left out of an archive with a warning in the journal, as a copy leaves one out, and a download of one alone is refused with 400. The file's folder is reached by handles and its name opened as an `O_PATH` handle without following a link, which reads nothing; only when `fstat` on that handle finds a regular file is the file reopened from it, through `/proc/self/fd`, for reading (`services.OpenRegularForRead`). So a FIFO, socket or device is never opened for reading, whatever is put at the name in between. The editor's read opens its file the same way.

Creating a btrfs subvolume in a folder the admin picked (`storage.btrfs_subvolume_create_in`) reaches that folder the same way and creates through its handle (`btrfs.CreateSubvolumeIn`), so that route is registered with the same `linksafe.ActingFor` rule as the file browser. The walk lives in `backend/bridge/internal/linksafe`, outside the file browser, for that reason.

The trash and its `.trashinfo` are the user's to edit, so `Path=` cannot say where root puts an item back. When a root process trashes an item for the session user it also records where the item came from in `/var/lib/linuxio/trash/<uid>/<dev>-<ino>.json`, a folder only root can write, one file per item named by the trashed item's device and inode (which a rename inside the trash keeps), written atomically, at most 10000 per user (past that stale records are dropped, and failing that the item is trashed without one). A restore on a root bridge uses the record and ignores `Path=`; the record goes when the item is restored or purged, and every purge drops the records of items no longer in the trash, as after another program emptied it. A purge leaves a record less than a minute old alone, since a record is written just before its item moves into the trash; it removes what an interrupted write left in the folder; and it keeps the record of a trash that is missing because its disk is not mounted, until the user reaches the limit. An item without a record, trashed by a desktop file manager or by a bridge that was not root, goes into a folder the session user does not own only when the restore request names that destination for that item in `confirmedDestinations`, a map from the trashed item's path to its destination, so a destination confirmed for one item does not admit another whose `Path=` was rewritten to it: the Trash view gets `confirmRestore` for such an item and asks "Restore to <path>?" before it sends the request, and the server refuses the restore without it. The other protections stay: only an item the user could not have written goes into such a folder, staged under a hidden name first. A bridge that is not root reads no records, as it cannot, and restores as before. Sizing a trashed folder for its Properties (`filebrowser.trash_size`) takes only an item of the session user's own trashes, reaches it as a purge does and walks it through handles without following a symlink or entering another mount (told by `statx` `STATX_MNT_ID`, Linux 5.8 and later; below that the size is refused rather than walked), so root measures nothing outside the item; inside it the walk is root's, so on a session with sudo it also counts the parts the session user could not read, as sizes and counts only, never names.

A restore whose name is taken may keep both or replace (see [Trash](./trash.md#when-the-name-is-taken)). The choice changes only the name or what is replaced, never which folder an item may enter: back where it came from, an item refused into a folder the user does not own is refused before anything at its name is touched, and one admitted there is staged and checked first whatever the choice. Two more rules hold for a replace back where the item came from, since what it goes over would otherwise be the user's to pick: an item without a record replaces only the destination `confirmedDestinations` confirms for it, so a `Path=` rewritten after the page asked replaces nothing (it could name a folder root owns inside one of the user's folders, which a merge would then fill with the user's files); and a folder does not merge into a folder the user does not own, nor into any folder inside one, since the could-have-written check vouches for the top of the item only, not for what a merge moves in below it, and a merge would put the user's entries where the user may not write. A replace works through the handle of the folder it opened, so a link at a name inside it is replaced, never written through. A restore into a folder the request names (`destination`) is different: that folder, and the name each item takes there (`names`, or its name in the trash, never `Path=`), are the admin's choice in this request, not a claim read from the trash, so it is a move the admin asks for now, as `filebrowser.move_batch` is when they move the item out of the trash folder by hand, which the could-have-written refusal already points them to. The folder must exist and is reached from `/` under the link rule above, the item goes in by rename (not to another filesystem, never over what is at its name unless the request said `overwrite`), and neither `confirmedDestinations` nor the could-have-written rule applies to it; the page sends `destination` only for a folder the admin picked.

Root cannot sign in to LinuxIO: `linuxio-auth` refuses uid 0 after PAM has resolved the account (`backend/auth/linuxio-auth.c`, "root login is not allowed"), and `packaging/etc/linuxio/disallowed-users` lists root for the PAM stack as well. The root-session case of `actingFor` is a guard, and the trash list and purge, which decide the rule from the process uid alone, agree with it.

### Paths through links

The page sends a path as it navigated it, through whatever links led there, and the URL and the breadcrumbs keep that path. The bridge resolves the folders of such a path where the request hands it over (`linksafe.ResolveFolders`; a folder a change writes into, its own name included, with `linksafe.Resolve`; a read with `iteminfo.ResolveSymlinksAt`), and the code below works on the result, a path whose folders held no link when it was resolved. The reads and checks there go through Go's `os.Root`, opened at `/`, which refuses a link with an absolute target such as `/home/u/data -> /mnt/data` and so failed everything below one. At `/` that refusal is all `os.Root` adds, so resolving first takes no guarantee away. It also makes `CheckNotProtected` and the mount-point check judge an entry where it really is: through a link to `/`, `/srv` is still a system folder. What the bridge answers names the path the page sent.

What a resolution follows depends on what the request does:

- A read (a listing, the Permissions dialog's stat, the editor's read, a download, a download of several items as one archive, and for an admin folder sizes and search) follows every link, for every session, as relative links always were: what it finds goes to the person who asked, never into a folder another user can write.
- A change on a bridge that is not root follows every link too: the bridge is the session user, and the kernel checks that user's permissions.
- A change on a root bridge resolves under the rule above: a link in a folder root alone can write is followed, any other is refused with the 403 that names where it leads. So an admin reads below `~/data -> /mnt/data` but changes nothing through that name, and "Open the real folder" takes them to `/mnt/data`; the editor opens a file there read-only, since its save would be refused. The resolved path is only a name: the change reaches it again from `/` by handles under the same rule, so a folder on it swapped for a link after the resolution is refused then, not followed.

A `..` the page sends after a link is taken on the path as sent, `/home/u/data/..` being `/home/u`, as the breadcrumbs show it. A `..` inside a link's target, of a folder on the way or of the last name, is taken where the link leads, as the kernel takes it: `L -> c/../x`, where `c` is itself a link, leads to `x` beside where `c` leads.

One resolution is bounded as one path lookup by the kernel is: it follows at most 40 links in all, wherever they sit (a folder on the way, the last name, inside another link's target), and a loop or a longer chain fails with `ELOOP`. Since a link's target can name some two thousand folders, it also opens at most 4096 names before it fails with `ENAMETOOLONG`, which no path a person browses comes near; os.Root bounds its walks the same way. A resolution where a request's path enters, and every read's, stops between two names when its request is cancelled, so a listing of a folder full of crafted links costs at most that much per link and ends with the request. The handle walks a change makes itself (`linksafe.OpenDirNoUserLinks`, `linksafe.OpenNearestDirNoUserLinks`) take no cancel and run to their bound of 40 links and 4096 names.

### Lock files

A lock a root process takes lives in `/run` (`/run/linuxio-fstab.lock`,
`/run/linuxio-shares.lock`, `/run/linuxio-rsync.lock`,
`/run/linuxio-docker-update.lock`), or beside the state file it guards under
`/var/lib/linuxio`: folders root alone writes. `/run/lock` and `/var/lock`
are world-writable with the sticky bit, so any local user can create the
lock file there first. Root then cannot open it at all
(`fs.protected_regular`), or the user holds its `flock` for good, and the
privileged operation it guards, an fstab or share edit, never runs.
`TestNoLockLivesInAWorldWritableFolder` in `backend/common/filelock` fails on
a path in either folder. `/run` is a tmpfs, so a lock left by an older
LinuxIO under `/run/lock` is gone at the next boot.

### In the frontend

The server's 403 is the gate; the page only avoids offering what will be refused. A control whose route is privileged is hidden for a session without sudo, read from `useAuth().privileged` or a route's `requiresPrivileged` access policy, and a privileged read that a page mounted for such a session would make is not issued. What is gated today:

- the power menu, the dashboard's hostname and clock edits, and the unit actions on the Services page;
- the Accounts page: adding users and groups, editing, password, lock and unlock, group members and delete, and ending a session; the lists and each user's details and activity stay;
- the network interface card, which shows the same settings (connection, IPv4 method, addresses, gateway, DNS, search domains, MTU, optional at boot) as text with no control and no save;
- the Docker pages, the Docker components and the dashboard's Docker card: every container, image, network, volume and compose stack change, Start all, Stop all and Prune, the container terminal and updates; the lists, details, inspect views, logs and update checks stay, and a stack's compose file opens read-only. A user in the `docker` group reaches these pages without sudo, since the capability probe pings the Docker socket as the bridge's user;
- monitoring history (`monitoring.get_*_history`): the live charts on the dashboard and the network page skip their backfill and fill from live samples, and the history cards on the Hardware, Network and Docker pages say the history needs a privileged session (`useHistoryAccess`, `useLiveSeries`);
- the Settings tabs whose reads are all privileged (Indexer, Monitoring with its Logging card, Notifications and Power: `indexer.get_config`, `indexer.get_status`, `monitoring.get_config`, `monitoring.get_status`, `logging.get_debug`, `alerts.get_notifications`, `power.get_status`): the tab is hidden and a `?tab=` link to it falls back to General, so none of those reads is issued;
- the dashboard's Memory overflow dialog, withheld for a different reason: its read, `memory.get_swap_status`, is unprivileged (it reads `/proc`, `/sys`, `/etc/fstab`, the zram tools' configuration files and dpkg's status file, asks TuneD whether it runs and, with both zram tools installed, systemd which one runs zram, and returns nothing sensitive: of the zram configuration, only paths, device names and the size settings of zram-generator's other files), but every action in it is privileged (`memory.set_swap_mode`, `memory.set_swappiness` and `memory.drain_swap` stop swap units, hold them off at boot with a drop-in under `/etc/systemd/system` and write under `/etc` and `/proc/sys`), so a session without sudo would see a dialog it cannot use. The Swap row of the Memory card is the edit button that opens it only for a privileged session, and the dashboard's `?dialog=memory-overflow` opens it only for one ([Memory overflow](./memory.md#who-sees-it));
- a run's saved output (`tasks.output`): the History page shows no output section, and the Schedules tab, whose `schedules.list` is privileged too, is hidden. The dashboard's failed-login alert and the dialog that reads `system.list_failed_login_events` only exist for a privileged session, because `system.get_health_summary` leaves the alert out for any other;
- the file browser's search, folder sizes and Index filesystem (`filebrowser.search`, `filebrowser.subfolders`, `filebrowser.dir_size`, `filebrowser.index`): the search field and the index action are hidden and sizes show as unknown. A trashed folder's size in the Trash's Properties is not one of them: `filebrowser.trash_size` walks an item of the session user's own trash, as that user on a bridge that is not root ([Trash](./trash.md#the-list)).

Search stays admin-only by decision: the index covers the whole host and only root can reach it, so a session without sudo would need a root component that filters every result by what the user may list.

## Testing

Dispatcher tests should cover:

- privileged route with unprivileged session returns forbidden
- privileged route with privileged session runs
- forbidden starts do not create Tasks
- forbidden starts are typed errors

A file browser test that needs root, such as one that acts for another user, skips itself otherwise and has a name that ends in `AsRoot`: the root suite (`make vm-test-filebrowser-root`, `FILEBROWSER_ROOT_RUN` in `mk/quality.mk`) runs tests by that name, so one named otherwise never runs as root.

See [API Contract](./api-contract.md) for route declaration and registration details.
