# LinuxIO Agent Instructions

## Simple, idiomatic code

- Prefer the smallest coherent change that fixes the root cause and follows the surrounding package or component. Favor the standard library, existing dependencies, and existing project boundaries over unrelated refactors or speculative extensibility. Add a helper, interface, wrapper, or configuration option only when it creates real reuse, a needed ownership or test boundary, or materially simpler call sites.
- In Go, prefer synchronous, explicit control flow. For request-scoped, I/O, or blocking work, take the caller's `context.Context` first and propagate it. Handle errors with useful operation context, preserve identity with `%w` when callers may use `errors.Is` or `errors.As`, and do not panic for ordinary runtime or input failures. Every goroutine needs a clear owner, cancellation path, and exit condition.
- Logging (`log/slog`, journald sink; guarded by `backend/common/logging/style_test.go`):
  - Levels: Error (3) a request, task, or daemon failed and someone must look (router, task runner, HTTP middleware, fatal exit); Warn (4) degraded but continuing, or a 4xx; Info (6) one line per completed host mutation or daemon lifecycle event; Debug (7) reads, progress, request traces.
  - Log or return, never both: code that returns an error does not log it (the bridge router and task runner log every failed route and task); code that swallows an error logs it.
  - The reason is in MESSAGE: the journald handler appends the `error` attribute once, so never concatenate errors or values into the message.
  - Messages are lowercase constant text (a leading acronym or product name from the `logguard` allow-list is fine), no trailing punctuation, no `[Tag]` or `Prefix:`; context goes in attributes and the error key is `error`, never `err`.
  - The one exception: in `backend/common/dockerupdate` (`containerNamedPaths` in `logguard`), a line about one container ends its message with the name, `"... container " + name`, and keeps the `container` attribute holding the same expression, since a timer run's saved output shows messages without attributes. See `docs/docker-updates.md`.
  - Client errors wrap a status sentinel with `%w`: `ErrInvalidArgs` 400, `ErrForbidden` 403, `ErrNotFound` 404, `ErrConflict` 409; `bridgeipc.NewError` only where the code itself is the point.
  - Success is one Info line per completed host mutation, past tense, identifiers as attributes; progress and reads are Debug.
- In React, keep rendering pure and derive values instead of mirroring props or query data in state. Use Effects only to synchronize with external systems, with complete dependencies and cleanup; handle user actions in event handlers. Keep server state in TanStack Query, shareable URL state in validated TanStack Router search or path parameters, and transient UI state locally. Reuse generated query options and route helpers, preserving their invalidation and cancellation paths. Treat memoization as an optimization, not a default. Don't add `useCallback`/`useMemo`/`memo` outside `*Virtual*` files or props consumed by them; the compiler handles it. Existing ones may be removed when touching the file, confirming with `make compiler-coverage`. The compiler skips a component that returns a bare array (`items.map(...)`) and `make compiler-coverage` does not report it; return a fragment so its rows are cached (`FolderRows` in `components/pathpicker/DirectoryTree.tsx` says what that costs).
- A dialog that starts a long job (a `MutationTask` that reports progress) does not hold itself open while the job runs: Close and Escape work, the other controls stay held, and the task tray keeps the progress and the cancel. A dialog whose write takes a moment stays held, since it is where the error and the retry are. See `docs/jobs.md`.
- In the frontend, style through the shared `components/ui` components and the `--app-*` CSS variables `AppThemeProvider` writes to `:root` (`theme/variables.css`, `theme/cssVariables.ts`). Outside `components/ui` and `theme/`, code does not call `useAppTheme()`, compute colours with `alpha()`/`darken()`/`lighten()`, branch on `palette.mode`, or set hex colours or `fontSize` inline; `test/guards/styling-boundary.test.ts` lists the few files that must hand a browser API a resolved colour (canvas charts, xterm, ace, colour editors) and fails on any new one.
- The backend targets Linux; do not add portability layers without a concrete requirement. Prefer Go APIs and existing D-Bus or service abstractions over shell commands. When a subprocess is necessary, use the existing context-aware command path, pass arguments separately, honor cancellation and timeouts, and return useful stderr with the error. Treat optional host facilities as capabilities so their absence does not break unrelated features, keep privileged mutations narrow and validated, and distinguish unit tests from tests requiring systemd, Docker, libvirt, root, or a real host.
- Every route whose handler needs root (writes under `/etc` or `/var/lib`, mounts, block-device or filesystem ioctls, systemd, NetworkManager, Docker, libvirt, PackageKit, user and group changes, power) must declare `apischema.Privileged()` in its binding, so the dispatcher refuses it with 403 for a non-sudo session instead of the handler failing with a permission error part-way through. Reads stay unprivileged unless they expose sensitive data. See `docs/privilege_pattern.md`.
- Docker access is root-equivalent and the `docker` group is kept empty by policy, so every Docker write (containers, images, networks, volumes, compose stacks, daemon settings) declares `Privileged()`; never rely on group membership for Docker access. See `docs/privilege_pattern.md`.
- The scheduled Docker update pass never builds an image: a Compose service built on the host is rebuilt only from the Containers page, where an administrator watches it. See `docs/docker-updates.md`.
- The base images of an image built on the host are read from the build's own output (`base_images.go`), never from the Dockerfile or anything else in the build context, which root would be opening in a folder other users may write; a moved base is reported and never acted on. See `docs/docker-updates.md`.
- A lock file a root process takes lives in `/run` or beside its state file under `/var/lib/linuxio`, never in `/run/lock`, `/var/lock` or another folder other users can write, where a local user can create the file first and block the privileged operation it guards; `TestNoLockLivesInAWorldWritableFolder` (`backend/common/filelock`) fails otherwise. See `docs/privilege_pattern.md`, "Lock files".
- LinuxIO is server administration software that other people install, so a threat or bug that needs a second local user, a hostile process of the session user or a session without sudo is in scope, and is never set aside as "single-user only".
- The owner is the only user today, so saved files, configuration formats and API shapes may change without a migration or legacy-key handling; say plainly what breaks on upgrade. This does not cover data-safety behaviour, such as which snapshots or files get deleted.
- LinuxIO has one authenticated door: webserver → `auth.sock` → PAM → bridge. A root action on behalf of a user happens in `linuxio-auth` after PAM or inside an existing root component, never through a new socket that other local users can connect to; the only world-connectable socket is the read-only metrics API. `linuxio-bridge` takes no verb. See `docs/process-systemd-architecture.md`.
- `linuxio-auth` has an SELinux domain of its own (`packaging/selinux/linuxio.cil`), and the RPM's post-install step loads the module and relabels the binary at every install and upgrade. The module gives `linuxio_auth_t` no permission `unconfined_service_t` lacks other than the transition into `unconfined_t` (and the entrypoint of its own file), its constraint stays, and anything not needed for sign-in goes in an `optional` block. A denial is not answered by dropping `pam_selinux`'s `open` line or by `SELinuxContext=` on the unit, and a line added to one PAM file (`packaging/etc/pam.d/linuxio`, `linuxio.rhel`) goes into the other. See `docs/process-systemd-architecture.md`, "SELinux".
- `linuxio` is the only program an administrator types, and it holds admin commands only (status, logs, start, stop, restart, verbose, version). What a systemd timer, hook or drop-in needs done as root is a word of `linuxio-worker`, never a command of `linuxio`, a word on a daemon or a new binary with words; daemons start with flags only, and the programs systemd runs as root are installed `0700` (`packaging/scripts/package-root.sh`) so no other user can run them. A release which changes a command line LinuxIO writes on save rewrites the saved copies in the package's post-install step. See `docs/process-systemd-architecture.md` and `docs/packaging.md`.
- A file LinuxIO writes for its own work or its own setting (a timer, a drop-in naming a LinuxIO program, its own APT or time-server file) is deleted at package removal: its exact path is in the lists of `packaging/debian/postrm` and the RPM's `%postun`, and a test of its writer (`TestPackageRemovalDeletes*`) holds both to it. What LinuxIO writes for an administrator's own setup (scheduled scripts, the rsync service, Docker's drop-ins, the memory page's files) runs without LinuxIO and stays. A DEB purge deletes `/etc/linuxio` and `/var/lib/linuxio`, so a file there that such a setup reads is in the postrm's `admin_state` list, held by a `TestPackagePurgeKeeps*` test of its writer. A unit whose text depends on no setting is a package unit, and a save writes only its timer. See `docs/packaging.md`, "Removal".
- The notices a package installs are written by the build from what it linked and bundled (`packaging/scripts/third-party-notices.sh`), so a Go module or npm package is never added to `docs/THIRD_PARTY_NOTICES.md` by hand; that file holds only what no tool sees: code adapted from another project, an icon set, the source link of an MPL part. See `docs/packaging.md`, "Third-party notices".
- Neither package strips, splits or rewrites a program: the webserver checks the SHA-256 of `linuxio-bridge` recorded at build time, and `package-contents.sh` compares all nine with the build. See `docs/packaging.md`.
- A release is built only in the pinned images of `packaging/build/pins.env`, and the pins of the images, Node and the Go tools move only through `make update-build-pins`; an action's commit moves through it or through Dependabot's weekly pull request. See `docs/releases.md`.
- Every program other than `linuxio` answers `--help`, `-h` and `--version` and nothing else meant for a person: through `version.Program` in Go and the same text in `linuxio-auth`, with no `help` or `version` word and no `-v`. Flags are written with two dashes, and a flag several programs share has one name (`--config`, `--verbose`). `linuxio-claude-relay` answers only while `LINUXIO_CLAUDE_BIN` is unset; in a chat every argument is Claude Code's. A `0700` program answers "Permission denied" to another user, on purpose. See `docs/process-systemd-architecture.md`, "Binary invocation map".
- Every process LinuxIO starts for an Assistant agent (the chat, the Terminal sign-in, the `claude plugin` commands) gets the variables of `acpagents.Profile`, so each agent keeps its sign-in, settings, plugins, history and memory in `~/.local/share/linuxio/profiles/<id>` and never in the `~/.claude`, `~/.gemini` or `~/.codex` the user's terminal and editor use; a start without them splits the Assistant's state between the two. See `docs/AI-assistant.md`, "Profile".
- Every Assistant agent's chats work in its profile folder (`WorkInProfile`), never in the home, whose `.claude`, `.gemini` or `.codex` is the user's own profile: an adapter reads that folder's settings by itself whatever the CLI is told (`claude-agent-acp` takes the model from `~/.claude/settings.json` despite `settingSources`), and the home reaches the agent as a further workspace folder. See `docs/AI-assistant.md`, "Profile".
- A WireGuard interface goes up and down by starting and stopping `wg-quick@<name>.service`, never by running `wg-quick` from the job host: a job host runs with `NoNewPrivileges=yes`, under which a tool its distribution confines with AppArmor cannot change profile, and the flag stays, since it is also what keeps the commands the root host runs as the signed-in admin (npm, `claude plugin`) away from `sudo`. The one exception takes down an interface its unit does not hold. See `docs/wireguard.md`.
- A kernel setting a WireGuard interface needs (IPv4 forwarding) is set by LinuxIO before it starts the unit and kept for boot in `/etc/sysctl.d/90-linuxio-wireguard.conf`, never by a `sysctl` line in a hook: Ubuntu's profile for `wg-quick` refuses the write, `sysctl` exits 0 all the same, and the interface comes up with peers that reach nothing behind the server. See `docs/wireguard.md`, "Forwarding".
- An `x-systemd.*` option on a pool's `/etc/fstab` line reaches systemd, for a mount that exists, only through libmount's record of the mount under the device the kernel names as its source, which mount(8) often writes under another member and a `mount(2)` by LinuxIO not at all: never count on the line alone to keep a pool mounted when a disk goes, leave the record to `unbindPoolMounts` (`backend/common/btrfs/fstab_bound.go`), and write `x-systemd.device-bound=false` only where `btrfs.UnboundMountsHonoured` says systemd reads it as written (255; an older one binds the mount harder for it). See `docs/btrfs.md`, "Pools".
- A file operation never waits for the index: the bridge reports it done when the filesystem work is done, tells the indexer afterwards, and the indexer answers a move or the refresh of an opened folder at once and applies it in its turn. A size answer says when it is not final (`pending`), and the page asks again. See `docs/indexer.md`, "Sizes that are still catching up".
- The index database has one writer at a time, ordered by the indexer daemon's work queue: the scanner (`linuxio-indexer --index-mode`, run by `linuxio-indexer-index.service`) asks the daemon for its turn over the socket and holds it until it ends, and nothing else (the bridge, a second scanner, a new unit) writes the database or scans without that turn. See `docs/indexer.md`, "Full index".
- The indexer looks at a path a request names through `indexing.Lstat` or `openScanRoot` (`backend/indexer/internal/indexing`), which open every folder on the way without following a symlink; never `os.Lstat`, `os.Stat` or `os.Open` on the full path, which let another local user choose what root records under a path of the tree. See `docs/indexer.md`, "Mutation reconciliation".
- A search inside a folder also reads that folder's tree on disk, read-only and within its budget (`liveSearchBudget`, at most `maxLiveSearches` at once), through the scan's own opens (`indexing.SearchTree`) on a goroutine the search stops waiting for after its grace; it never writes the index or queues work, a complete answer keeps every index result still on disk rather than trusting the Go matcher to be the SQL one, and a search from `/` reads the index only. See `docs/indexer.md`, "Search inside a folder".
- For storage, use kernel interfaces first (ioctls through `x/sys/unix`, `mount(2)`, superblocks) and pin every kernel struct with a request-number test; use `btrfs-progs` only where the kernel has no interface, and add no third-party btrfs library. The UI exposes every choice the backend makes instead of picking defaults silently. See `docs/btrfs.md`.
- Every operation that writes a device checks it with `deviceInUse` (`backend/bridge/handlers/storage/device_free.go`) and adds only its own rule on top; btrfs `force` erases an old filesystem and never a member of a btrfs pool, md array or LVM volume group, mounted, running or active or not, and Initialize disk erases an md or LVM member only when the request confirms it; the automatic rebuild erases a member's own returned disk only after its identity and stability checks, and nothing else erases a pool member without a person. udev does not probe a disk while LinuxIO holds its lock, so a check that decides on md or LVM membership also reads the device's own signature (`backend/common/btrfs/member.go`, through an exclusive open) right before the write, under the disk lock where the operation takes one, and LinuxIO's own write to a device opens it exclusively, never plainly after an exclusive check (a GPT entry beside partitions in use is the exception). See `docs/btrfs.md` and `docs/storage-disks.md`.
- A btrfs operation on a path from the top level takes the top-level mount and the path apart and reaches the path through `openBelow` (`backend/common/btrfs/below.go`), then works through that one handle; never open, ioctl or rename `filepath.Join(top, path)`, which follows a symlink another local user put in a folder of the pool. See `docs/btrfs.md`.
- A shared folder's `smb.conf` section, its export and its ACL are written from its record (`/etc/linuxio/shared-folders.json`) and never changed on their own; its access is applied to the folder itself and to what is made in it afterwards, never to what is already there; and a password reaches Samba only at the moment LinuxIO sets it (`shares.SyncSambaPassword`), never from `linuxio-auth` at sign-in. See `docs/shared-folders.md`.
- `linuxio-snapshots` and each source's folder in it are root's alone (`ensureSnapshotDir`), since a snapshot keeps the permissions its files had; only a shared folder's earlier versions open one, by an ACL (`btrfs.SetSnapshotsACL`), never a mode. What is deleted from a recycle bin is chosen by a file's ctime and by the time a run first saw a folder there, noted on the folder in an attribute only root writes, and removed through handles (`btrfs.RemoveOlderThan`), never by a time a user can set or by path. See `docs/btrfs.md` and `docs/shared-folders.md`.
- `smbd` announces itself and its Time Machine folders to Macs only when it starts, so a change of what it announces restarts it (`timeMachineChanged`, `SetSMBSettings`); nothing else restarts it, since a restart cuts every open connection. See `docs/shared-folders.md`, "Time Machine".
- A memory-overflow change adds swap before it removes any (a resize adds a temporary swap file beside the file first when the file is the only swap device or its data needs the room), removes swap only after the room check on a freshly read status, restarts zram at a new size only while disk swap is active, and never undoes added swap in a rollback. It turns off, resizes, drains or deletes only a swap file that an `/etc/fstab` line names by its plain path (or the temporary file a resize made beside one), where every folder on that path is one root owns that no group or everyone may write and the file is a regular file root owns (`rootOnlyPath`, `openRootOnlyFolder`), and that is not the hibernation file, and the zram its provider runs; it creates a swap file only at `/var/lib/linuxio/swap/swapfile`; a partition, an LVM volume and any other swap are shown and never turned off. See `docs/memory.md`.
- A root file browser operation acting for a session user reaches its folders through `linksafe.OpenNearestDirNoUserLinks` or `entryFollowingNoUserLinks` and then works through handles; it follows a symlink only in a folder root owns that no group or everyone may write, and refuses any other naming where it points, with no "follow anyway". It removes a folder by a name it chose earlier only through `removeAllAtIf`, which checks that the name still holds that folder. See `docs/privilege_pattern.md`.
- A file browser path from a request has its folders resolved where it enters, with `linksafe.ResolveFolders` (a folder written into, whole, with `linksafe.Resolve`), for `actingFor(session)` when it changes files and for no owner when it only reads, before anything reaches it through `os.Root`, which refuses a link with an absolute target; a read opens its file through `services.OpenRegularForRead`, which decides on the opened handle that it is a regular file, and responses keep the path the page sent. See `docs/privilege_pattern.md`.
- A folder is watched only while a page shows it, by one inotify watch on the listed folder's handle in the session's bridge (`filebrowser.watch`), never recursively and never from the indexer. See `docs/filebrowser-live-listing.md`.
- A move to the Trash frees no disk space, and the page says so where the move is made and wherever the Trash is reached (the delete question, its toast, the Trash button, the Trash). Those sizes are read from the index and never from a walk, and what every folder view asks for (`filebrowser.trash_usage`) looks for trashes on local mounts only, never on a network filesystem or an automount point with nothing mounted on it. See `docs/trash.md`, "Disk space".
- File browser operations follow Windows File Explorer: folder conflicts merge, a same-folder paste makes "name (copy)", delete goes to the trash before anything permanent, and failures are reported per item. Prefer the safe default even when it costs a prompt.

## Task execution and architectural authority

- An implementation specification supplied with the task is the approved product and architecture direction: validate it against the working tree, adapt minor differences to existing patterns, and do not re-plan it. If the repository fundamentally conflicts with it (the result would be incorrect, unsafe, or architecturally invalid), report the conflict instead of silently redesigning.
- Preserve the security and responsibility boundaries between `linuxio-webserver`, `linuxio-bridge`, and `linuxio-auth`; never move privileged or authentication-sensitive behavior across them for convenience.
- Use subagents only for bounded, independent work; keep integration, conflict resolution, final diff review, and final decisions in the main agent. Parallel agents must be read-only or own disjoint files.
- At the start of a subagent-driven run, say which model plans, builds and reviews. Prefer faster, lower-cost models for page and UI tasks, and give a task that touches privilege boundaries, record stores, concurrency or the test VM a stronger builder.
- The owner edits and commits in the same checkout during long runs, and a commit of theirs can take an agent's uncommitted hunks with it. Check `git log` and `git status` between tasks, build a task's review diff from its own paths only, and say so when one of their commits captured agent hunks.
- An `isolation: "worktree"` agent may get a worktree based on `main` instead of the current branch, and a worktree at HEAD lacks uncommitted work. Compare each worktree's HEAD with `git rev-parse HEAD` before using its patch, or create the worktree yourself from HEAD.
- Never run Make concurrently with implementation or with another Make invocation in the same worktree.

## Required quality workflow

- Every LinuxIO code change must be linted and tested before handoff.
- Use repository Make targets for Go, frontend, C, generation, build, and test workflows. Never invoke their underlying tools directly, including `npm`, `tsc`, `go test`, `gofmt`, `golangci-lint`, `govulncheck`, `vitest`, `oxlint`, or `oxfmt`.
- If one of those project workflows lacks a required focused target, add or improve a Make target.
- Run lightweight file-level tools required by higher-level instructions—such as `shellcheck`, `shfmt`, `actionlint`, `jq`, and `rg`—directly. Their use alone does not justify adding a Make target.
- Prefer the narrowest `*-quiet` target that fully covers the current work.
- Frontend-only changes: iterate with focused targets and finish with `make check-frontend-quiet`.
- Backend-only changes: iterate with focused targets and finish with `make check-backend-quiet`.
- Changes spanning frontend and backend, generated API contracts, shared build tooling, or unclear ownership boundaries: run `make test-quiet`.
- For claims that depend on real browser navigation, chunk loading, or browser behavior, additionally run `make test-frontend-browser-quiet`. Run `make setup-frontend-browser-quiet` first only when its browser dependency is not already installed.
- Before the browser tests, check that port 4174 is free and that no `vite preview` is left from an earlier run; a timing assertion that fails while another session's run overlaps is rerun when the machine is quiet. See `docs/development.md`.
- Data-safety storage work (degraded mounts, resync, replace, split brain) starts from what upstream does (kernel, btrfs-progs, mdadm, systemd), gets an independent review, and adds a root test on loop devices to `make test-btrfs-integration`; unit tests against the fake kernel are not kernel-level verification.
- Checks that need root, a real kernel, systemd or reboots run in the disposable VM (`make vm-*`, see `docs/development.md`). An agent runs only the suite or spec file its change needs: one root suite with `make test-vm-backend SUITES=<suite>` or a `vm-test-*` target (after a change under `backend/common/btrfs` that issues ioctls, `make vm-test-btrfs-integration`), and one spec file on one VM with `make test-vm-browser VMS=1 PLAYWRIGHT_ARGS=<spec>`, or `make test-vm-browser-rerun VM=N PLAYWRIGHT_ARGS=<spec>` on the VM that run used. The full `make test-vm-backend` and `make test-vm-browser`, and `make test-vm-all`, which runs both on Ubuntu and then Fedora's part of each, and `make test-full`, which runs `make test`, the host browser tests, the assistant agent install test and `test-vm-all`, take too long for an agent; they are the owner's to run, and the handoff names the one worth running. An agent has no sudo on the host, so `make test-btrfs-integration` and `make test-filebrowser-root` there are the owner's to run too. VM targets lock only the VMs they act on, and a test target given no `VM` picks free VMs itself, creating one when the others are busy and memory allows, so run the plain target, and `VM=N` only to return to a VM your run already used. A VM a run created (its first line says so) joins the VMs that `vm-install`, `vm-reset`, `vm-stop`, `vm-update` and `test-vm-browser-rerun` act on, so the agent runs `make vm-destroy VM=N` when done unless the owner asked to keep it. The targets touch only the `linuxio-e2e*` domains; never touch any other domain on the host.
- A change to a systemd unit or socket, a PAM file or SELinux policy is verified in the VM as the package installs it and again after a reboot; a drop-in or an edit on a running system does not show what a fresh start does. See `docs/development.md`, "Test VM".
- A check that needs a live chat through `claude-agent-acp` on the owner's Claude login is the owner's to run: write the script and hand over the exact command.
- Report the exact Make target or targets run and their results. Call out any target that could not run, distinguish introduced failures from pre-existing or environmental failures, and do not claim browser/runtime coverage from source inspection or unit tests alone.

- Quiet targets retain complete logs in `.cache/test-logs/`; inspect those logs after a failure before rerunning with normal output.

## Generated files and contract changes

- Do not hand-edit `frontend/src/api/generated/*` or `frontend/src/routeTree.gen.ts`.
- When Go-owned API contracts or generator inputs change, use `make generate` and then validate the combined result with `make test-quiet`.
- Trace contract, router, and query-ownership changes through their callers, invalidation paths, cancellation paths, tests, source guards, and canonical documentation rather than changing one layer in isolation.

## Documentation

- `docs/README.md` is the index of implemented behaviour, and its Code column names the code each doc covers. Before designing or changing a subsystem, read the docs that cover the files you will touch; `scripts/docs-for.sh <path>...` lists them. Plans that have not shipped are in `docs/TODO`.
- The code is the truth. When a doc and the code disagree, say so and fix the doc in the same change instead of following the doc.
- A behaviour change updates the docs that cover it in the same change.
- Write a new doc in `docs/` when a change adds a subsystem, a host integration, a protocol or file format, or a decision the code cannot explain by itself, and no existing doc covers it; when one does, extend that doc instead. A doc states what the system does and why, not how the change was reached. Plans, phases and open work go in `docs/TODO` and move up when they land.
- An open item goes in `docs/TODO/backlog.md` only when someone would hit it in normal use or it is a safety matter (data loss, privilege, another local user): once, in the section it belongs to, and deleted when it is fixed. A file of its own in `docs/TODO` is only for a plan that is not built yet; do not start a second list.
- A finding from a review or a test that a few lines fix is fixed in the same change, not filed. The backlog receives only what needs the owner's decision, a larger change or a real host.
- A limit that is by design, or an edge case nobody is expected to hit, is one line under "Known limits" in the doc that covers the feature, and is not repeated in the backlog. A change that was proposed and turned down, and is likely to be proposed again, is one line under Rejected in the backlog with its reason. An observation with no consequence is written nowhere. At handover, name each limitation and where it was written.
- Adding, removing or renaming a doc, or moving the code it covers, updates its row in `docs/README.md` in the same change; `make check-docs` fails otherwise.
- A rule learned during a session that applies to anyone working on LinuxIO becomes one line in this file, with its reasoning in the doc that covers the area. Do not leave it only in agent memory.

## Reviews and cleanup

- Before handoff, run a general code review of the diff, not only the privilege checklist, check a reviewer's "this is safe" before repeating it, and review the fixes again. The main agent reads risky code a subagent built itself; a subagent's review is an addition to that.
- Add or update tests for behavior changes. Reconcile audit resolution text and checkboxes when the implementation lands.
- Before removing code that looks like a compatibility wrapper or legacy API, inspect callers, generated references, history, and production reachability; do not delete it based on naming alone.
- ZFS is not supported in the UI, but the monitoring agent's ZFS ARC collector and its payload fields stay; add new memory fields beside them and do not remove them as cleanup. See `docs/monitoring.md`.
- Keep conclusions scoped to the evidence gathered. Clearly separate source-verified findings, automated-test results, and runtime-observed behavior.

## Git and handoff

- Never create, amend, or push a Git commit. Leave commit creation to the user.
- When coding work is complete, always present a concise suggested commit message for the resulting changes, even though no commit is created automatically. Do this only when actual code has been changed and not in exploratory reviews/comments.
